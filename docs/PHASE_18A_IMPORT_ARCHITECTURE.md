## 1. Current academic model (as it exists today)

```
UniGameSaveData (v2, localStorage "unigame:saveData:v1")
├─ semester: SemesterRecord            ← the ONE academic-facts store
│   ├─ label, timezone, startDate/endDate/examPeriod (ConfirmableValue)
│   └─ subjects: SubjectRecord[4]      ← FIXED set of 4, fixed ids:
│        "user-interface-design" | "cloud-based-web-application-development"
│        | "project-management" | "professional-practices-and-entrepreneurship-in-it"
│       ├─ code: ConfirmableValue<string>
│       ├─ modules: ModuleRecord[12]   id = "<prefix>-module-<01..12>"
│       └─ assessments: AssessmentRecord[]  id = "<prefix>-assessment-<n>"
│                weight/dueDate/dueTime: ConfirmableValue<T>
│                dueWindowRaw, dateKind, sourceFile
├─ tasks: TaskRecord[]                 ← ONE per module ("module-task-<id>"),
│                                          type:"milestone"; assessments have
│                                          NO task twin (surfaced directly)
├─ assessmentProgress: UserAssessmentProgress[]  ← one per assessment id
├─ reminders: ReminderRecord[]         ← origin:"auto" (deterministic id,
│                                          regenerated by syncAutoReminders
│                                          from CONFIRMED dueDate+dueTime
│                                          only) or "user" (hand-created,
│                                          untouched by sync)
├─ studyLog, activeFocusSession, completedFocusSessions, mentorBonds,
│  milestones, completionCelebratedAt, userProgress, settings
```

**The subject id set is fixed and art-bound.** `public/assets/manifest.json`
has exactly 4 `room-<subjectId>` scenes and 4 `mentor-<subjectId>` sprites;
`src/components/room/roomPersona.ts` has exactly 4 personas (+ one generic
fallback). No code path can render a room, a mentor, or subject-coloured UI
for a subject id outside this set. **This is the single most important
constraint on the whole import feature**: an imported "5th subject" has
nowhere to live in the game world.

**Derivation, not storage.** Progress %, priorities (`lib/priority.ts`),
achievements, relationships, room-evolution stage, the semester calendar
(`lib/semesterCalendar.ts`), and the Calendar panel's event list
(`lib/calendarEvents.ts`) are *all* recomputed from `semester` + `tasks` +
`assessmentProgress` on every render. **This means import doesn't need to
touch Tasks/Calendar/Reminders/mentor-dialogue/room-evolution directly at
all** — writing correct data into `semester` (and, for genuinely new
modules, a matching `tasks` entry) is sufficient; every other system
re-derives itself automatically. Confirmed by reading `lib/reminders.ts`'s
`syncAutoReminders`, which is invoked from a `useEffect` in
`SaveDataContext` keyed on `saveData.semester` — any semester change already
regenerates deadline reminders from confirmed dates with no new reminder
code required.

**NEEDS_CONFIRMATION discipline.** Every fact not "clearly confirmed" is
`{ value: null, status: "needs_confirmation" }` (`ConfirmableValue<T>`,
`unconfirmed<T>()`/`confirmed<T>()` helpers). `deriveConfirmationStatus` and
`deriveReminderSchedule` are *always* recomputed from the constituent fields
after any write — never hand-set — so a record can never drift out of sync
with its own weight/date/time. `AssessmentRecord.dateKind` already
distinguishes `exact | week_only | placeholder_in_source | source_conflict |
missing` — the exact vocabulary Part 5/6 of this phase need; **no new
enum is required, the domain already anticipated this.**

**Existing import/export code** is exactly one thing: whole-save JSON
export/import (`persistence.ts` `exportSaveDataAsJson` /
`importSaveDataFromJson`, wired in `SaveDataContext.importSaveData`). It
replaces the *entire* save after writing a pre-import backup to
`unigame:saveData:backup-preimport` (`IMPORT_BACKUP_KEY`). **This is a
different concern from academic-document import** (whole app state vs.
syllabus/calendar facts) and must stay untouched and unconfused with the new
system — Settings still exposes "Export save data" / "Import save data" for
full-save portability; the new Semester Setup flow is additive academic
*content* import that merges into the existing save via ordinary mutations,
the same way `confirmAssessmentDueDate` etc. already work.

**Save migration/backup behaviour** (for reference, unchanged by this
phase): version 1→2 auto-migrates on load with a raw backup to
`unigame:saveData:backup-v1`; every field has a per-field coercer in
`sanitizeSaveData` that repairs or defaults rather than rejecting the whole
save; "additive fields don't need a version bump" is the established
pattern (used for `milestones`, `completionCelebratedAt`, Phase 7's focus
fields, RC1's `onboardingHintDismissed`) — **this phase follows the same
pattern for any new save field.**

**Current onboarding.** `WorldShell.tsx` shows a one-time 3-step coach mark
in HQ (`settings.onboardingHintDismissed`, dismiss-forever) — pure UI
guidance, no data setup. There is currently **no "first-launch data setup"
of any kind** — the app always boots with the seeded 4-subject/48-module/14-
assessment 2026-Semester-2 dataset from `src/data/semesterData.ts`. Genuinely
empty vs. populated therefore cannot be detected from save shape alone (the
seed is never actually "empty") — Part 7 needs an explicit trigger flag
rather than a heuristic (see §7 below).

**Entry surface.** `MenuPanel.tsx` (Phase 15B/16/17) is a flat, text-labelled
list — Profile / Achievements / Statistics / Settings / Help / Save data —
opened from the 4th primary tab. This is exactly where "Semester Setup" is
added as a 7th list item (no new tab, no new HUD element, consistent with
the "readable text labels rather than icons alone" instruction already
followed here).

## 2. Fields required by UniGame vs. fields commonly available in source files

| UniGame field | Typically found in | Confidence when found |
| --- | --- | --- |
| Subject name | Unit outline title, handbook entry | high |
| Subject code | Unit outline header/footer (e.g. "CSE2UI") | high if explicit |
| Coordinator | Unit outline "Coordinator/Lecturer" line | medium |
| Module/week title+topic | Weekly schedule table | high if a table exists, low if prose |
| Assessment title | Assessment section heading | high |
| Assessment weight (%) | Assessment table "Weighting" column | high in tables, low in prose |
| Assessment due date | Assessment table, or a separate calendar/ICS | **varies hugely** — this is the #1 source of `NEEDS_CONFIRMATION` in the existing seed too (see `SEMESTER_DATA.md`: only 5 of 14 real assessments have a confirmed exact date) |
| Assessment due time | Rarely given without a date; ICS files are the reliable source | low from prose, high from ICS |
| Submission method | Assessment section prose | medium |
| Semester start/end | Academic calendar page, rarely the unit outline itself | low–medium |

This table is the direct justification for confidence levels being a first-
class part of the candidate model (§4) rather than a UI afterthought: the
existing real seed data already demonstrates that syllabus PDFs routinely
give weight without an exact date, or a week number without a date at all.

## 3. Mapping rules (candidate → live save)

1. **Subjects never mint new ids.** An `ImportedSubjectCandidate` must be
   explicitly mapped by the user (Review step) to one of the 4 existing
   `SubjectRecord.id`s, matched by (a) exact code, (b) normalized name
   similarity, offered as a suggestion, never silent. A candidate the user
   does not map is excluded from Apply and shown as "not supported — no
   room exists for this subject yet" (documented limitation, §9).
2. **Modules** match an existing module by `weekNumber`/`moduleNumber`
   first, then by normalized title similarity. A match offers a field-level
   merge (topic/description) subject to the conflict rules in §6; no match
   → append a new `ModuleRecord` (id `<prefix>-module-<NN>`, next free
   number) **and** a mirror `TaskRecord` (`module-task-<id>`, `type:
   "milestone"`, `xpReward: 10`) — replicating `createDefaultModuleTasks`
   exactly so imported modules behave identically to seeded ones.
3. **Assessments** match by `assessmentNumber` + subject, then by title
   similarity. A match merges only fields that are currently
   `needs_confirmation` on the live record, UNLESS the user explicitly
   resolves a conflict (§6) — a *confirmed* live value is never silently
   overwritten. No match → append a new `AssessmentRecord` (id
   `<prefix>-assessment-<n>`, next free number) **and** a mirror
   `UserAssessmentProgress` default entry, replicating
   `createDefaultAssessmentProgress`.
4. **Calendar/ICS events** that match an assessment (by title similarity +
   date proximity) supply/confirm that assessment's `dueDate`/`dueTime`
   (highest-confidence source for dates, per §2). Events that match nothing
   become `ReminderRecord`s with `origin: "user"` (so they are never
   silently deleted by the auto-sync) and `sourceWindow` set to the
   original text — **reusing the existing reminder store**, not a new
   calendar-event table.
5. **"Week 6" is never converted to a date** unless `semester.startDate` is
   confirmed (existing `ConfirmableValue`) — mirrors the rule already
   documented in `SEMESTER_DATA.md` for the hand-authored seed.
6. Confirmed values already in the live save are **source-priority 1**
   always; nothing an import supplies can silently demote a confirmed field
   without an explicit conflict resolution (§6).

## 4. Risks

- **Wrong-subject placement** if title-similarity matching is too loose →
  mitigated by requiring explicit user confirmation of every subject
  mapping in Review; no automatic subject creation.
- **Silent overwrite of user progress/confirmed data** → mitigated by the
  transaction design (§8): confirmed fields are never overwritten without
  an explicit conflict choice; grades/progress/completion are untouched by
  Apply (Apply only ever writes to `semester` + adds new `tasks`/
  `assessmentProgress` *entries*, never mutates existing progress fields).
- **Fabricated dates/times** → mitigated by the deterministic extractor's
  hard rules (§5 of the brief; never infer a time from a date-only source,
  never resolve `week_only` without a confirmed start date).
- **Oversized/hostile files** (huge PDFs, zip bombs disguised as DOCX,
  malformed ICS) → mitigated by the file-ingestion layer (size limits,
  type sniffing, try/catch around every parser, never `eval`/`innerHTML`
  raw content).
- **Scanned/image-only PDFs producing near-empty text** → detected (very
  low extracted-character count relative to page count) and surfaced as a
  clear "this looks like a scanned document; text extraction found very
  little — OCR isn't available yet" warning rather than silently importing
  nothing.
- **Bundle size** from PDF/DOCX parsing libraries → mitigated by code-
  splitting: the Semester Setup flow and each document provider's parser
  library are dynamically imported only when that provider is actually
  used, matching the existing "secondary screens are lazy-loaded" rule in
  `ARCHITECTURE_GUIDE.md`.

## 5. Data ownership & privacy boundaries

- All parsing in this phase is **100% client-side** (pdf.js and mammoth
  both run in-browser via WebAssembly/pure JS; the hand-rolled ICS/JSON/text
  parsers are plain string processing). No file, extracted text, or
  candidate data leaves the device in this phase — there is no network call
  anywhere in the MVP import path.
- The optional AI extraction adapter (Part 11) is **interface-only** in this
  phase: no implementation is wired up, no API key is requested from or
  stored in the browser, and the interface itself documents that any future
  call must go through a backend/serverless function with explicit,
  separate user consent before any document leaves the device. Local-only
  mode is therefore the *only* mode that exists right now, not a fallback.
- Import drafts (in-progress candidate packages) are stored in their own
  localStorage key (`unigame:importDraft:v1`), separate from the main save,
  so a large in-progress draft never bloats or risks the primary save file,
  and clearing it is a single, safe operation.
- University-web-search and LMS providers (Canvas/Moodle/Blackboard/
  Brightspace) are **typed placeholders that throw/return
  "not configured"** — they are never presented as available, never invoked,
  and never contact any external host in this phase.

## 6. Provider contract (summary — full types in `src/import/types.ts`)

`AcademicProvider` exposes: `id`, `displayName`, `capabilities` (readonly
input-kind flags), `isAvailable()` (sync capability probe — real for
document providers, `false` for placeholders), `validate(input)` (cheap
pre-check before committing to extraction), `extract(input, ctx)` (async,
`ctx` carries an `AbortSignal` for cancellation and an `onProgress`
callback), and structured errors (`ImportError` with a `code` union, never a
bare thrown string, so the UI can render a specific, friendly message per
failure kind). The import manager (`ImportManager.runAll`) fans a set of
provider inputs out, collects each provider's `ImportedSourcePackage`
(subject/module/assessment/calendar candidates + warnings), and hands the
combined list to the merge engine (§ Part 6 of the brief) to produce one
`AcademicImportPackage`.

## 7. Import transaction design

**Draft phase (pre-Apply):** all extraction/merge/review happens against the
in-memory `AcademicImportPackage` plus its optional localStorage-backed
draft copy. Nothing here touches `UniGameSaveData`.

**Apply phase (the only phase that touches the live save):**
1. Validate the normalized package (every included item resolved, no
   unresolved conflicts among *included* items — matches "no one-click
   Import Everything while conflicts remain unresolved").
2. `backupCurrentSave(saveData)` — **reuses the existing
   `IMPORT_BACKUP_KEY`/`backupCurrentSave` function used by whole-save
   import**, so there is exactly one "previous save" backup mechanism in
   the app, not two parallel ones.
3. Build a diff summary (added / updated / skipped / conflicted counts) and
   show it as the final confirmation, per the brief.
4. Apply as one synchronous, pure `(save) => save` reducer
   (`applySemesterImport`) — same style as every existing mutation in
   `saveDataMutations.ts` — so it either fully succeeds or the caller never
   calls `setSaveData` at all (no partial-write state is representable).
5. On any thrown error during the reducer, the caller catches it, **does
   not** call `setSaveData`, and shows a friendly error; the live save is
   therefore never touched on failure (rollback is "don't commit", which is
   simpler and stronger than "commit then undo"). The draft package is kept
   so the user can retry after fixing the offending item.
6. "Undo last semester import" restores from `IMPORT_BACKUP_KEY` **only
   while that key still holds the pre-apply snapshot** (same one-step-back
   semantics `BACKUP_GUIDE.md` already documents for whole-save import) —
   surfaced as long as the key exists and matches the last-applied-import
   marker.

**Why no save-version bump:** every field Apply writes into (`semester`,
new `tasks` entries, new `assessmentProgress` entries, new `reminders`
entries) already exists in v2 with established coercers. The one genuinely
new concept — persisted personal goals (Part 10) — is a small additive
object following the exact precedent of `completionCelebratedAt`/
`milestones` (Phase 11): a new optional field with a permissive coercer,
defaulting cleanly on any save that predates it. No existing field changes
meaning, so no version bump is warranted.

## 8. Rollback strategy (explicit)

| Failure point | Recovery |
| --- | --- |
| A provider throws during extraction | That source is marked failed with a readable error; other sources continue; draft package retains everything already extracted |
| User cancels mid-processing | `AbortSignal` propagates to the active provider; partially-processed sources are dropped, already-finished ones are kept |
| Apply validation fails (unresolved conflict slipped through) | Apply never starts; user is returned to Review with the offending item highlighted |
| Apply reducer throws (defensive — should not happen given validation) | `setSaveData` is never called; save is untouched; draft is retained; friendly error shown |
| User regrets a completed Apply | "Undo last semester import" restores the pre-apply backup, one step, while available |
| Draft becomes stale/corrupt in localStorage | Read through the same per-field-coercion discipline as the main save; unreadable → treated as "no draft", never crashes the app |

## 9. Known scope limitation carried forward from this audit

Because rooms/mentors are art-bound to exactly 4 fixed subject ids, this
phase's import **cannot add a 5th playable subject**. Any candidate subject
that doesn't match one of the 4 (by explicit user choice) is captured,
shown, and explicitly excluded from Apply with a clear explanation — never
silently dropped, never forced into a room that doesn't exist for it. This
is a genuine product constraint, not an oversight, and is called out again
in the completion report's "known extraction limitations."

## 10. Where imported data enters the existing system (exact seams)

| Imported thing | Enters via | New code needed? |
| --- | --- | --- |
| Subject code/description | `confirmSubjectCode`-style mutation, extended | Extend, don't duplicate |
| New module | Append to `semester.subjects[i].modules` + append matching `TaskRecord` | New `applyImportedModule` reducer, following `createDefaultModuleTasks` shape |
| New/updated assessment | Append/merge in `semester.subjects[i].assessments` + matching `UserAssessmentProgress` if new | New `applyImportedAssessment` reducer, following `confirmAssessment*` + `createDefaultAssessmentProgress` shape |
| Confirmed date/time/weight | Same `ConfirmableValue` + `withRederivedStatus` pattern already used by `confirmAssessmentDueDate` etc. | Reuse existing helpers directly |
| Standalone calendar event | New `ReminderRecord`, `origin: "user"` | Reuse existing `addUserReminder`-shaped construction |
| Reminders/Calendar/Priority/Timeline/mentor dialogue/room evolution | **Nothing** — all derive automatically from the above | None |
| Personal goals | New additive `personalGoals` save field | New, small, additive |
| Academic setup suggestions | Computed strings shown in the flow, not persisted | None (pure derivation, like Priority Centre) |

This table is the load-bearing conclusion of the whole audit: **the import
feature's job is almost entirely "produce well-formed writes into fields
that already exist," not "build new storage."**
